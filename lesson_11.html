00

Одна ссылка — и чужой аккаунт

Представьте: сайт отправляет пользователю письмо со ссылкой для сброса пароля. Адрес содержит «случайный» код. Откуда взялось это число? И можно ли его угадать?

Ситуация

Случайно выглядеть — недостаточно

Если адрес example.org/reset?token=... можно предсказать, злоумышленник получит возможность подобрать рабочую ссылку. Даже очень длинный набор символов может быть бесполезен, если он создаётся из воспроизводимой последовательности.

01
Непредсказуемость

Нельзя вычислить следующий секрет по предыдущим.

02
Достаточное пространство

Угадывание должно быть практически неосуществимым.

03
Правильное хранение

Секрет нельзя выдавать через логи или повторно использовать.

🧩 Аналогия: замок и ключ

Длинный токен похож на сложную форму ключа. CSPRNG отвечает за то, чтобы нельзя было угадать, какой ключ изготовят следующим. А защита сервера — за то, чтобы ключ не оставили на столе. Нужны все три свойства.

Главный вопрос лекции: чем отличается случайность для игры в кости от случайности для ключа шифрования? Ответ определяет выбор модулей Python.
01

Карта понятий: от энтропии до токена

Лекция объединяет две линии: откуда берётся непредсказуемость и как эта непредсказуемость представляется в байтах и строках.

Анимированные стрелки показывают логический поток данных; схема упрощена: конкретная реализация CSPRNG зависит от операционной системы.
Линия 1

Как получить секрет

Системный источник случайности → криптографически стойкий генератор → нужное количество случайных байтов.

Линия 2

Как передать секрет

Байты → HEX или Base64 → строка, которую удобно хранить в базе или передавать в URL. Кодирование не добавляет защиты.

02

PRNG vs CSPRNG: похожие числа, разная гарантия

Псевдослучайный генератор (PRNG) создаёт последовательность по алгоритму и начальному состоянию seed. Криптографически стойкий генератор (CSPRNG) тоже обычно алгоритмический, но спроектирован так, чтобы его выход нельзя было практически предсказать.

PRNG

Mersenne Twister, random

Очень удобен для моделирования, игр, статистики и воспроизводимых экспериментов.

Пример: задайте random.seed(42) и получите ту же последовательность в том же окружении.

Большой период ≠ защита от восстановления состояния. У MT19937 период 219937 − 1, но это не делает его криптостойким.

CSPRNG

Системный генератор, secrets

Создаёт значения, которые должны оставаться непредсказуемыми для противника даже при знании алгоритма и наблюдении других результатов.

Пример: токен сброса пароля, ключ или криптографический nonce (с учётом требований протокола).

Безопасность требует правильного начального состояния, защиты состояния и корректной реализации.

🎲 Аналогия: кино и реальная жеребьёвка

Запись бросков кубика на видео выглядит случайной, но если начать воспроизведение сначала, результат будет тем же. Это похоже на PRNG с известным seed. Для выдачи пропуска в серверную нужна не «убедительная запись», а результат, который нельзя заранее вычислить.

Лаборатория 01 · детерминизм

Воспроизведи последовательность

Здесь используется учебный LCG — не Mersenne Twister. Идея та же: одинаковый seed даёт одинаковый поток.

Интерактивно
Нажмите «Получить 8 чисел».

Учебный LCG иллюстрирует детерминизм, но не воспроизводит алгоритм Python random.

PYTHON · воспроизводимость ≠ секретность
import random
import secrets

random.seed(42)
print([random.randint(0, 9) for _ in range(5)])

random.seed(42)
print([random.randint(0, 9) for _ in range(5)])  # точно такой же список

# Для секретов:
print(secrets.token_hex(16))  # 16 случайных байтов = 128 бит
Вызовы random.seed() полезны для воспроизводимости теста, но опасны при генерации токенов.
Важно: PRNG не обязательно «плохой» или статистически слабый. MT19937 хорош для ряда незащищённых задач. Но криптостойкость — отдельное свойство, которое не выводится из равномерности или длины периода.
03

Как противник использует предсказуемость

Атакующий часто не знает пароль пользователя. Ему достаточно получить несколько результатов слабого генератора и восстановить способ получения следующего значения.

Шаг 1. Приложение создаёт токен

Вместо безопасного генератора разработчик берёт random, иногда дополнительно задавая seed из времени.

Шаг 2. Часть выходов становится наблюдаемой

Например, случайные значения видны в идентификаторах, ссылках, игровых результатах или ответах API.

Шаг 3. Атакующий строит модель состояния

Если алгоритм и достаточные выходные данные известны, возможна реконструкция состояния генератора — по крайней мере в определённых сценариях.

Шаг 4. Будущие секреты становятся предсказуемыми

Сервер продолжает работать, но «случайные» результаты могут оказаться известны заранее.

MT19937 · разбор тезиса со слайда

Почему часто упоминают число 624?

У стандартного Mersenne Twister есть состояние, состоящее из 624 32-битных слов (с дополнительным индексом). При наблюдении достаточного количества последовательных полных 32-битных выходов можно обратить операцию tempering и реконструировать состояние. После этого становятся предсказуемыми последующие результаты.

Схема концептуальная. Не любые 624 результата Python API достаточно: важно, чтобы были известны именно подходящие последовательные 32-битные выходы.

Практический вывод: замена random на secrets — обязательное архитектурное решение для секретов, а не «косметическая» правка.

PYTHON · безопасная иллюстрация проблемы seed
import random

# Учебный пример: один и тот же seed → один и тот же результат
first = random.Random(2026)
second = random.Random(2026)

print([first.getrandbits(32) for _ in range(4)])
print([second.getrandbits(32) for _ in range(4)])
# Списки совпадут полностью.
Угадать seed и восстановить состояние MT19937 — разные атаки. Важно понимать обе, но не смешивать их: для восстановления состояния seed может быть неизвестен.

05

str, bytes и bytearray: что компьютер хранит на самом деле

До криптографии нужно разобраться в данных. Компьютер обрабатывает биты, а Python предлагает разные типы для человека и для бинарного мира.

str

Человеческий текст

Последовательность символов Unicode. Строка неизменяема.

Пример: "Привет". Для получения байтов требуется кодировка, обычно UTF‑8.

bytes

Бинарные данные

Неизменяемая последовательность чисел от 0 до 255.

Подходит для хешей, ключей, сетевых пакетов, шифртекста, файлов.

bytearray

Изменяемые байты

Похож на bytes, но отдельные байты можно заменять на месте.

Полезен для обработки буферов и построения бинарных сообщений.

📦 Аналогия: смысл, коробка и пластилин

str — слово, которое мы понимаем. bytes — коробки с числами, в которых хранится закодированное слово. bytearray — те же коробки, но содержимое можно переставлять. Кодировка объясняет, как перейти от смысла к конкретным числам.

Лаборатория 02 · Unicode → UTF‑8 → HEX → биты

Исследователь байтов

Напишите слово или символ. Смотрите, почему «один символ» не обязательно равен одному байту.

Интерактивно
—Кодовых точек Unicode
—Байт UTF‑8
—Длина HEX (символы)
В этой визуализации «символы» считаются как кодовые точки Unicode. Комбинируемые символы и эмодзи могут занимать несколько кодовых точек даже при отображении одним знаком.
PYTHON · типы и кодировки
text = "Привет 🔐"        # str: символы Unicode
raw = text.encode("utf-8")  # bytes: двоичные данные

print(text, type(text))
print(raw, type(raw))
print(len(text), len(raw))   # количество символов и байтов различается
print(raw.hex())            # печатный HEX без изменения данных
print(raw.decode("utf-8")) # bytes → str

buffer = bytearray(b"Hello")
buffer[0] = 0x68            # H (0x48) → h (0x68)
print(buffer)               # bytearray(b'hello')

b1 = b"\x00\xffA"
b2 = bytes([0, 255, 65])
b3 = bytes.fromhex("00ff41")
print(b1 == b2 == b3)      # True
Переход str → bytes выполняется через encode(), обратный — через decode(). Для криптографических функций формат данных должен быть определён явно.
Тонкость UTF‑8: для ASCII один символ часто кодируется одним байтом; для кириллицы обычно двумя, а для многих эмодзи — четырьмя или больше байтами. Число байтов определяется кодировкой, а не количеством видимых символов.
06

XOR: операция, которая отменяет сама себя

Побитовое исключающее ИЛИ (XOR, ^) возвращает 1, когда биты различаются, и 0, когда равны. Эта операция часто встречается внутри криптографических алгоритмов.

Таблица истинности

ABA XOR B
000
011
101
110

Почему XOR обратим

(A ⊕ K) ⊕ K = AK ⊕ K = 0, а A ⊕ 0 = A

Чтобы отменить XOR с ключом, достаточно выполнить XOR с тем же ключом ещё раз. Это математическое свойство, а не гарантия защищённого шифрования.

💡 Аналогия: переключатель света

Представьте восемь лампочек, каждая либо горит (1), либо выключена (0). Бит ключа 1 переключает лампу, 0 — оставляет как была. Применение одного и того же переключателя дважды возвращает исходную картину.

Лаборатория 03 · побитовая математика

XOR под микроскопом

Измените число или ключ и проследите каждый из восьми битов. Нажмите на биты ключа, чтобы переключить их.

Интерактивно
A ⊕ K = C; C ⊕ K = A
PYTHON · XOR для одинаковых по длине буферов
import secrets

def xor_bytes(a: bytes, b: bytes) -> bytes:
    if len(a) != len(b):
        raise ValueError("Буферы должны иметь одинаковую длину")
    return bytes(x ^ y for x, y in zip(a, b))

message = b"HELLO"
key = secrets.token_bytes(len(message))

ciphertext = xor_bytes(message, key)
restored = xor_bytes(ciphertext, key)
print(restored == message)  # True
Демонстрация свойства XOR. В реальном приложении не следует самостоятельно конструировать шифрование из XOR: используйте стандартные проверенные криптографические протоколы.
Критическое отличие: просто XOR с повторяющимся паролем не является безопасным шифром. «Одноразовый блокнот» (OTP) требует действительно случайного ключа не короче сообщения, строгой секретности ключа и однократного использования. Повторное использование ключа опасно.
07

HEX и Base64: как упаковать бинарные данные в текст

Веб-адреса, JSON и сообщения не всегда удобно передают произвольные байты. Поэтому данные кодируют в строку. Это не изменяет их секретности: любой может декодировать результат.

HEX

16 символов алфавита

Каждый байт представлен двумя шестнадцатеричными цифрами.

0x41 → 41, 0xff → ff. 16 байтов становятся 32 символами.

Base64

6 бит на символ

Три байта обычно превращаются в четыре символа Base64; в конце может быть выравнивание =.

Удобно для текстовых протоколов и файловых вложений.

URL-safe Base64

Для адресной строки

Алфавит Base64 с заменами + → - и / → _. В токенах завершающие = часто убирают.

Не путать с URL-кодированием и шифрованием.

Лаборатория 04 · кодировщик в браузере

Один текст — три представления

Сначала текст превращается в байты UTF‑8, затем в HEX или Base64. Нажмите «Декодировать», чтобы получить исходный текст.

Интерактивно
UTF‑8 → HEX
—
UTF‑8 → BASE64
—
URL-SAFE BASE64
—
ВОССТАНОВЛЕННЫЙ ТЕКСТ

Данные кодируются и декодируются локально с помощью Web API браузера.
PYTHON · все три представления
import base64

raw = bytes(range(16))

hex_text = raw.hex()             # '000102...0f'
hex_back = bytes.fromhex(hex_text)

base64_text = base64.b64encode(raw).decode("ascii")
base64_back = base64.b64decode(base64_text)

url_text = base64.urlsafe_b64encode(raw).decode("ascii")
url_back = base64.urlsafe_b64decode(url_text)

assert raw == hex_back == base64_back == url_back
print(hex_text)
print(base64_text)
print(url_text)

Кодирование

Делает данные удобными для хранения или передачи. Ключ не нужен. Например, любой получатель Base64 может восстановить байты.

Шифрование

Скрывает содержание от тех, кто не обладает ключом. В практических протоколах применяют проверенные схемы, например AES‑GCM, с соблюдением требований к nonce и управлению ключами.

Критическая ошибка: хранить пароль как Base64 — почти то же, что хранить его открытым текстом. Пароли пользователей обычно проверяют через специальный алгоритм хеширования паролей с солью и параметрами замедления, а не через обратимое кодирование.
08

Энтропия Шеннона: сколько вариантов у противника?

Энтропия измеряет неопределённость вероятностного источника. Для криптографии особенно важно не путать идеальную модель случайного выбора с паролями, которые люди придумывают сами.

H(X) = −Σ pᵢ · log₂(pᵢ)Энтропия Шеннона для исходов с вероятностями pᵢ

Если каждый из N символов выбирается независимо и равновероятно, а длина пароля L символов, то количество комбинаций равно Nᴸ, а энтропия всей строки:

H = L · log₂(N)Применимо именно к равномерной независимой случайной генерации
PIN из 4 цифр
13,29

бит при равномерном выборе: 10⁴ = 10 000 вариантов

PIN из 6 цифр
19,93

бит при равномерном выборе: 10⁶ = 1 000 000 вариантов

Токен 16 случайных байтов
128

бит: 2¹²⁸ вариантов при корректном криптографическом генераторе

📚 Аналогия: угадай книгу в библиотеке

Если 16 книг равновероятны, нужно в среднем больше вопросов, чем если одна книга встречается в 90% случаев. Энтропия учитывает не только число исходов, но и вероятности. Поэтому «длинный пароль» вроде aaaaaaaaaaaa не получает автоматически высокую реальную стойкость.

Лаборатория 05 · математика неопределённости

Калькулятор энтропии

Выберите алфавит и длину случайно генерируемой строки. Ниже покажем ёмкость пространства вариантов.

Интерактивно
—Бит энтропии (идеальная модель)
—Число комбинаций
—Качественная оценка

Шкала — иллюстрация размера пространства поиска, не сертификат безопасности и не оценка конкретного человеческого пароля.

Вычисленное по частотам символов значение — эмпирическая энтропия на символ. Оно не оценивает защищённость токена или пароля от угадывания: короткий образец и структура языка дают искажения.

PYTHON · энтропия на символ в данных
from collections import Counter
from math import log2

def shannon_entropy(text: str) -> float:
    if not text:
        return 0.0
    counts = Counter(text)
    n = len(text)
    return -sum(
        (count / n) * log2(count / n)
        for count in counts.values()
    )

print(shannon_entropy("AAAA"))  # -0.0 (эквивалент 0)
print(shannon_entropy("ABCD"))  # 2.0 бита/символ

# Идеальный равномерный случайный токен:
length, alphabet_size = 20, 62
print(length * log2(alphabet_size))  # ≈ 119.08 бит
Функция измеряет разнообразие символов наблюдаемой строки, а не истинную мин-энтропию источника и не устойчивость пароля к словарным атакам.
Для 256-битного ключа важно, чтобы ключ действительно генерировался как 32 криптографически случайных байта. Запись «256 бит» сама по себе ничего не говорит, если исходные данные предсказуемы.

Откуда берётся криптографическая случайность в ОС?

Операционная система собирает непредсказуемые события из доступных источников, поддерживает защищённое внутреннее состояние генератора и предоставляет приложениям случайные байты через системные интерфейсы.

Наглядная модель. Точные источники и механизмы меняются между ОС, версиями ядра и аппаратными платформами.

Linux: системный генератор

Современный Python для получения системной случайности использует соответствующий интерфейс ОС; на Linux при наличии getrandom() вызов os.urandom() ждёт начальной инициализации пула случайности.

Историческое противопоставление /dev/random и /dev/urandom нельзя безоговорочно переносить на все современные ядра.

Windows: криптографический API

Современные версии Python используют системный криптографический источник Windows, например BCryptGenRandom(), а не самостоятельно написанный генератор.

В приложении Python предпочтительнее пользоваться готовыми функциями secrets, а не управлять системными вызовами вручную.

# В реальных системах НЕ журналируйте секретные ключи!
Важно для безопасности: качество случайности оценивают по источнику и алгоритму, а не тестом «выглядит хаотично». Нельзя взять предсказуемую строку и сделать её криптостойкой простым кодированием в HEX или Base64.

Генератор стойких паролей: длина важнее «магии символов»

Сила случайно созданного пароля определяется пространством возможных строк и корректностью генератора. Потребность во всех типах символов — вопрос конкретной политики, а не универсальное условие криптостойкости.

Хорошая стратегия

Равномерный выбор

Определите набор допустимых символов. Выбирайте каждый символ через secrets.choice(). При длине 20 и алфавите из 62 символов идеальная модель даёт около 119 бит.

Когда нужен каждый тип

Политика состава

Иногда сервис требует хотя бы одну цифру, заглавную букву и специальный символ. Это можно реализовать: обязательно выбрать по одному каждого типа, добавить остальные и перемешать с криптостойким выбором индекса.

Оценка по формуле L·log₂(N) применима к независимому равномерному выбору из общего алфавита. При обязательных категориях распределение другое: это ориентир, а не точный расчёт энтропии.

PYTHON · вариант A: простой и равномерный
import secrets
import string

alphabet = string.ascii_letters + string.digits
length = 20

password = "".join(secrets.choice(alphabet) for _ in range(length))
print(password)

# Для равномерного выбора из N символов:
# количество вариантов = N ** length
# оценка энтропии = length * log2(N)
Это простой безопасный базовый генератор при достаточной длине и правильном хранении полученного пароля.
PYTHON · вариант B: обязательные группы + Fisher–Yates
import secrets
import string
from math import ceil, log2

SPECIAL = "!@#$%^&*_-+"
GROUPS = [string.ascii_lowercase,
          string.ascii_uppercase,
          string.digits,
          SPECIAL]

def generate_password(entropy_bits=128):
    alphabet = "".join(GROUPS)
    length = max(len(GROUPS), ceil(entropy_bits / log2(len(alphabet))))

    # Гарантируем хотя бы один символ из каждой группы.
    pool = [secrets.choice(group) for group in GROUPS]
    pool += [secrets.choice(alphabet) for _ in range(length - len(pool))]

    # Fisher–Yates: случайная перестановка без modulo bias.
    for i in range(len(pool) - 1, 0, -1):
        j = secrets.randbelow(i + 1)
        pool[i], pool[j] = pool[j], pool[i]
    return "".join(pool)

print(generate_password())
Уточнение к слайду: формула L·log₂(N) здесь даёт ориентир сверху для полного равномерного алфавита, но не точное значение энтропии результата алгоритма с обязательными группами.
🔐 Аналогия: выигрышный билет

Если билет выбирается из гигантского набора независимо и непредсказуемо, угадать его трудно. Но если организатор всегда печатает похожие билеты, их длина не спасает. Поэтому популярные слова с заменами a → @ и o → 0 могут быть слабыми, даже если выглядят «сложно».

Практика эксплуатации: используйте менеджер паролей и многофакторную аутентификацию. Для серверного хранения паролей применяйте специализированные адаптивные хеш-функции (например, Argon2id), соль и актуальные параметры стоимости. Случайный токен и пароль пользователя — разные сущности.

Сравнение секретов и атаки по времени

Даже если токен хорошо сгенерирован, его можно проверить небезопасным способом. Типичный наивный алгоритм прекращает сравнение при первом несовпадении, а время проверки иногда выдаёт информацию.

В чём проблема раннего выхода?

Пусть сервер сравнивает полученную строку с эталоном символ за символом. Если первый символ неверен, проверка короткая; если совпало много символов, чуть дольше. При подходящих условиях и большом количестве измерений злоумышленник может использовать статистику времени.

🕵️ Аналогия: секретарь у двери

Вместо ответа «пропуск неверный» секретарь каждый раз говорит: «Первые три цифры правильные, на четвёртой ошибка». По сути, раннее время окончания проверки может непреднамеренно подсказать похожую информацию.

Кейс-задача: безопасная ссылка сброса пароля

Соединим все темы в один законченный сценарий. Пользователь просит восстановить доступ — система создаёт непредсказуемый токен и подтверждает его, не раскрывая внутреннее состояние.

Это учебная схема. В реальной инфраструктуре дополнительно нужны HTTPS, защита от злоупотреблений, доставка по подтверждённому каналу, мониторинг и атомарная фиксация использования токена.
1. Создание

Сервер генерирует 32 криптографически случайных байта и кодирует их в URL-safe текст. Размер исходного пространства — 2²⁵⁶, а не «длина URL в символах».

2. Хранение

В базе сохраняется хеш токена с привязкой к пользователю, сроком действия и статусом использования. Исходный секрет не сохраняется в открытом виде.

3. Доставка

Ссылка отправляется по проверенному каналу. Не показывайте токены в обычных логах или аналитике и контролируйте утечки через Referer и сторонние ресурсы.

4. Проверка

Сервер вычисляет хеш полученного токена и сравнивает его с сохранённым, проверяет срок действия и однократность. После применения запись должна стать недействительной.

PYTHON · мини-модель жизненного цикла токена
import hashlib
import secrets
from datetime import datetime, timedelta, timezone

# Учебное хранилище в памяти (не production БД)
reset_store = {}

def issue_reset_token(user_id: int) -> str:
    token = secrets.token_urlsafe(32)  # 256 случайных бит
    token_hash = hashlib.sha256(token.encode("ascii")).digest()
    reset_store[user_id] = {
        "hash": token_hash,
        "expires_at": datetime.now(timezone.utc) + timedelta(minutes=15),
    }
    return token  # в реальности отправить по защищённому каналу

def verify_and_consume(user_id: int, token: str) -> bool:
    record = reset_store.get(user_id)
    if record is None:
        return False
    if datetime.now(timezone.utc) >= record["expires_at"]:
        reset_store.pop(user_id, None)
        return False

    supplied_hash = hashlib.sha256(token.encode("utf-8")).digest()
    valid = secrets.compare_digest(supplied_hash, record["hash"])
    if valid:
        reset_store.pop(user_id, None)  # однократное использование
    return valid

# Мини-проверка:
code = issue_reset_token(123)
print(verify_and_consume(123, code))  # True
print(verify_and_consume(123, code))  # False: уже использован
Это учебный прототип. Для production нужны БД, атомарное использование токена, rate limiting, защита от перечисления пользователей, HTTPS, безопасная доставка и полноценный процесс смены пароля.

Почему здесь не надо «шифровать токен»?

Серверу необязательно расшифровывать токен. Он должен подтвердить, что предъявленное значение совпадает с выданным ранее. Достаточно стойкого случайного токена и безопасной проверки его хеша. Это уменьшает ущерб от некоторых утечек базы.

Указание SHA‑256 относится к хешированию высокоэнтропийного случайного токена. Для хранения человеческих паролей так делать нельзя: им нужен специализированный алгоритм хеширования паролей.

Шесть популярных заблуждений

Эти ошибки встречаются не только у начинающих разработчиков. Они помогают заметить проблемный дизайн ещё до появления кода.

«Если число выглядит хаотично, оно подходит для безопасности»
Нет. Статистическая случайность и криптографическая непредсказуемость — разные характеристики. PRNG может проходить статистические тесты и всё же быть полностью восстановимым из наблюдений.
«Очень большой период MT19937 делает его стойким»
Нет. Период показывает, когда повторится последовательность при корректном обходе состояний. Он не гарантирует невозможности предсказания следующего значения.
«64 HEX-символа — это 64 байта случайности»
Нет. Два HEX-символа кодируют один байт. 64 HEX-символа, полученные из 32 случайных байтов, несут 256 бит исходной случайности.
«Base64 можно использовать вместо шифрования»
Нет. Base64 — обратимая упаковка двоичных данных в текст. Декодирование общедоступно и не требует секретного ключа.
«Любой пароль с большими буквами, цифрами и знаками безопасен»
Не обязательно. Qwerty123! содержит разные типы символов, но предсказуем из-за шаблона. Главные факторы — случайность способа создания, длина, отсутствие повторного использования и качество хранения.
«secrets.compare_digest решает всю проблему аутентификации»
Нет. Он лишь снижает риск утечки информации во времени сравнения. Аутентификация также требует защиты транспорта, ограничения попыток, сроков действия, логирования событий без секретов и корректной работы с состоянием.
