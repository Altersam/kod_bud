Аутентификация ≠ авторизация

Инженерная задача

Ученик видит кнопку «Просмотр оценок», а учитель — «Изменить оценку». Если сервер ориентируется только на видимость кнопки, прямой HTTP-запрос может обойти это ограничение. Нам нужны проверяемые правила.

Граница модели

Для полноценной авторизации мало роли: нужно учитывать конкретного пользователя, действие, объект, контекст и принцип минимальных привилегий.

Важно: любой пример в курсе использует искусственные данные. Действия с настоящими сервисами допустимы только при наличии полномочий.

Как взаимодействуют части системы

Вместо магического «объект защищён» разбираем последовательность: кто выполняет действие, какая проверка применяется, что происходит со значением и что фиксируем в результате.

Понятия и пояснения

Аутентификация

Отвечает на вопрос «кто это?» — проверяет учётные данные или факторы входа.

Авторизация

Отвечает на вопрос «что этому субъекту разрешено сделать?» — проверяется при каждой защищаемой операции.

RBAC

Ролевая модель связывает группы разрешений с ролями. Хорошо подходит для учебных примеров, но требует детализации ресурсов.

IDOR / BOLA

Если изменение идентификатора ресурса открывает чужие данные, отсутствует объектная проверка доступа.

Принцип минимальных привилегий

Пользователь и сервис получают только те права, которые необходимы для выполнения задач.

Разделение ответственности

Класс Resource хранит состояние объекта, отдельный policy проверяет доступ, сервис выполняет действие только после проверки.

Практика Python: запусти и объясни

Каждый фрагмент запускается в Python 3 без сторонних зависимостей. Попробуйте изменить входные данные и предсказать результат до запуска.

01. Политика ролей: разрешённые действия

PERMISSIONS = {
    'student': {'view_own'},
    'teacher': {'view_own', 'edit_assigned'},
    'admin': {'view_own', 'manage_users'},
}

def allowed(role, action):
    return action in PERMISSIONS.get(role, set())

for role in ('student', 'teacher', 'admin'):
    print(role, allowed(role, 'edit_assigned'))
student False teacher True admin False
Разбор. Политика по умолчанию запрещает действие. В настоящей системе учитель также должен иметь право изменять конкретный класс или журнал.

02. Проверка владельца ресурса

def can_view_record(user_id, record):
    return user_id == record['owner_id']

record = {'owner_id': 17, 'grade': 5}
print(can_view_record(17, record))
print(can_view_record(19, record))
True False
Разбор. Смена ID в запросе не должна позволять читать чужие записи. На сервере всегда проверяем владельца и контекст.

03. Безопасный отказ и события аудита

def edit_grade(role, scope_allowed, grade):
    if role != 'teacher' or not scope_allowed:
        return {'status': 'DENIED', 'grade': None}
    return {'status': 'OK', 'grade': grade}

print(edit_grade('student', True, 5)['status'])
print(edit_grade('teacher', False, 5)['status'])
print(edit_grade('teacher', True, 5)['status'])
DENIED DENIED OK
Разбор. Учебная модель показывает две независимые проверки — роль и область полномочий. Реальная модель сложнее и должна тестироваться на негативных сценариях.

▣ Ситуация из практики

Ученик пытается открыть функцию редактирования чужих оценок через прямой запрос, даже если кнопку в интерфейсе ему не показывают.

Актив: Права на ресурс. Угроза: Повышение привилегий.

◉ Разбираем причинно-следственную связь

Скрытая кнопка не защищает серверный метод. Авторизация проверяется там, где выполняется действие, с учётом конкретного пользователя и ресурса.

Что проверяем: Запретить действие при отсутствии права.

⌘ Python · фрагмент для самостоятельной проверки

def can_edit_grades(role):
    return role == "teacher"

for role in ("student", "teacher"):
    print(role, can_edit_grades(role))
Ожидаемый результат: student False teacher True

Код запускается в Python 3 и использует только стандартную библиотеку. Эксперименты выполняйте на учебных данных и в разрешённом окружении.
